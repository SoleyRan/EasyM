# EasyM v0.3 第六步：PDF 引擎评估

评估日期：2026-10-13。分支：`feature/v0.3`。代码基线：第五步提交 `9a0310d`。应用版本仍为 0.2.0。

## 1. 决策

**v0.3 保留系统打印；专用 PDF 引擎集成延期。** 第六步完成的是有真实产物和可复现证据的评估，不新增“直接导出 PDF”菜单，也不捆绑浏览器或字体。下一步进入第七步统一回归、许可复核、0.3.0 版本更新与 Windows 开发包交付。

本轮比较现有打印 CSS、`pagedjs@0.4.3` 和 `pdfmake@0.3.11`。HTML 分页候选直接接入现有样式时出现内容截断与表头不重复，不能直接替换。结构化候选已验证中文排版、重复表头、字体子集和应用 CSP 下的浏览器 Worker，但需要完成字体回退、结构映射和分页策略后才能进入产品。后续若开发独立 PDF 输出，优先继续验证结构化路线；本记录不是对 pdfmake 的正式采用决定，也不代表其他引擎均不可用。

系统打印基线保留了压力样例的全部文本和完整大图片，没有观察到完全空白页；Letter 下大图片的标题与图片分离，仍属于已知分页限制。保留它并不表示三平台原生打印已验收。

## 2. 方法与边界

环境为 Windows `10.0.26200`、Intel Core 5 220H、16 个逻辑 CPU、31.7 GiB 内存、Node 24.20.0、Playwright Chromium `156.0.8078.4`。这是本机开发探针，不是 Windows WebView2、macOS WKWebView 或 Linux WebKitGTK 的真实打印对话框。

输入为未删改的 [办公导出](samples/v0.3/办公导出.md)、[降级与安全](samples/v0.3/降级与安全.md)，以及脚本确定性生成的压力样例：12 个中文标题/长段落、85 行表格、60 行代码及一条中英混合长代码、900×1800 PNG、emoji 与结尾标记。每个引擎分别生成 A4、Letter，共 **18 份 PDF、109 页**，全部经 Poppler 渲染；审查联系表和代表性完整页面，文本提取与渲染共同定位缺失、表头、孤行和空白页。

HTML 两路使用同一个生产 `parseDocument`、`createExport` 和 `export.css`。原始 HTML 不执行，缺失/远程/越界图片按现有 HTML 导出规则占位，授权样例 PNG 内联；安全样例没有先删除风险输入。分页前明确等待字体和所有图片解码。测试页使用应用 CSP，可信探针脚本由本机服务器提供；导出的静态 HTML 自身仍保持原有严格 CSP。系统 CSS 路用 Chromium 的 PDF API，代表现有打印 CSS 的 Chromium 基线，不能当作已点击原生“保存 PDF”。

pdfmake 路直接消费现有独立 AST/DOCX 中间模型，未从预览 DOM 推断结构。试验适配器映射段落、标题、列表、引用、表格、代码、分隔线和独立图片；未知结构保留静态原文。为测量运行路径，只提供 Noto 简体中文 Regular 字体，各种字体样式暂用同一文件；行内图片明确输出说明占位，代码也暂未映射等宽字体。这些是**适配器缺口**，不能据此断言引擎不支持这些能力。独立小图使用 `fit` 后会放大，也需要产品适配器补“不放大”尺寸规则。

## 3. 实际分页与完整性

页数先列 A4，再列 Letter；页数少不等于效果好。

| 方案 | 办公样例 | 安全样例 | 压力样例 |
| --- | --- | --- | --- |
| 现有系统打印 CSS / Chromium | 2 / 2 | 2 / 2 | 14 / 15 |
| Paged.js 0.4.3 | 1 / 2 | 2 / 2 | 13 / 13 |
| pdfmake 0.3.11 试验适配器 | 3 / 3 | 2 / 2 | 14 / 15 |

| 检查 | 系统 CSS 基线 | Paged.js 直接接入 | pdfmake 试验适配器 |
| --- | --- | --- | --- |
| 中文换行 | 审查页面可读；结尾中文存在 | 已生成部分可读；末尾丢失 | Noto 中文可读；结尾存在 |
| emoji 🙂 🚀 ✅ | 可见彩色字形，文本可提取 | 可见彩色字形，文本可提取 | 三个字符均无字体字形，显示方框/缺字 |
| 85 行表格 | 所有 ROW 标记在；表头重复 | 所有 ROW 标记在；仅第一页有表头 | 所有 ROW 标记在；表头重复 |
| 60 行和超长代码 | 所有 CODE 标记与长行首尾在 | 同左 | 同左；暂为比例字体，需独立代码样式 |
| 图片 | EM 图和大图完整；大图上下标记可见 | A4 办公样例从代码中间截断；压力样例大图消失 | 独立图完整；行内图为占位，小图被 fit 放大 |
| 结尾标记 | 两种纸张都存在 | 压力样例两种纸张均缺 FINAL-SENTINEL 和结束段落 | 两种纸张都存在 |
| 标题孤行 | 大图可能迫使标题独留前页，Letter 尤其明显 | 表头与正文分离；最后只剩“大图片”标题 | 表格/大图标题可能留在前页，需要 keep-with-next |
| 完全空白页 | 未观察到 | 未观察到，但有丢失内容 | A4 压力样例第 14 页完全空白；Letter 第 14 页是图片页 |

“无提取文本”不能直接判空白：系统 CSS Letter 第 14 页和 pdfmake Letter 第 14 页都有完整图片。检查脚本额外计算渲染像素覆盖率，保留 `blankTextPages` 与 `visuallyBlankPages` 两种记录。

Paged.js 的缺失是在等待图片解码后仍能复现的**当前样式兼容性失败**。本轮没有为它重写一套分页 CSS、添加表格 hooks 或改变样例去获得通过。它可能通过后续专门适配修复；在修复和三平台验证之前不能进入产品。

安全样例的差异也记录在证据中：现有 HTML 渲染会去掉原始 HTML/front matter 等节点，结构化中间模型将它们作为静态源文保留。这是已有导出契约差异，不是本步新增执行能力，也不能假定两种输出正文完全相同。没有观察到页面脚本执行、远程资源请求或将危险地址写为可执行链接。

## 4. 运行、取消、离线与成本

| 项目 | 系统 CSS 基线 | Paged.js | pdfmake |
| --- | --- | --- | --- |
| 压力样例生成 A4 / Letter | 393 / 394 ms | 613 / 626 ms，含加载分页 JS | 875 / 918 ms，Node Worker 纯生成 |
| 启动 | 共享测试 Chromium 启动约 173 ms | 在已有页面加载，包含在上列时间 | 压力样例 Node Worker 273 / 283 ms；浏览器 Worker 启动约 413 ms |
| 浏览器 Worker | 不适用，依赖 DOM/打印 API | 必须在 DOM 页面分页 | 真实 Worker 在应用 CSP 下通过；压力样例生成约 919 ms，产物 120,484 字节 |
| 取消 | 产品沿用原打印返回/Esc 与系统对话框 | 隔离测试页面关闭约 512 ms；未落盘 PDF | 就绪后终止生成 Worker 约 16 ms；未交付结果 |
| 故障恢复 | 本步不替代原生对话框验收 | 每次新建隔离页面，不复用坏分页 DOM | 缺字体文件明确失败；重建 Worker 后成功生成 120,366 字节 |
| 离线 | 字体和浏览器由系统提供 | 已下载 JS + 内联图片，0 个远程请求 | 本地字体 + 内联图片；资源 URL 访问策略禁用 |

这些是一次本机测量，不是 p95 或性能承诺。HTML 生成时间包括 PDF API；Node 测量不含模型生成和下载，浏览器 Worker 与 Node Worker 的时间不能直接混算。

压力样例 A4/Letter 的系统 CSS 浏览器工作集在生成后约 385/382 MiB，Paged.js 约 396/393 MiB；是 Chromium 进程工作集求和的前后两个采样点，共享页可能重复计算，**不是峰值、增量或 WebView 内存**。最后的页面 JS heap 分别约 3.1 MiB 与 5.8 MiB。Node Worker 报告约 444 MiB 的 `maxRSS`，这是整个共享 Node 主进程的生命期高水位，包含构建/其他运行，不能当作候选自身峰值。各字段和测量范围已写入 JSON；专用引擎正式采用前仍须隔离进程峰值测试。

| 额外资源 | 实测大小 | 分发含义 |
| --- | --- | --- |
| Paged.js 浏览器压缩 JS | 502,617 字节；gzip 97,258 字节 | 只负责分页 DOM，仍需打印后端；不自动提供三平台无对话框 PDF 文件 |
| pdfmake 浏览器压缩 JS | 1,053,972 字节；gzip 354,500 字节 | 不需附加 Node；可以按需加载到 Worker，必须另有字体/样式/资源适配 |
| NotoSansSC Regular OTF | 8,331,336 字节 | 当前测试的固定中文字体；单个字体加 pdfmake 原始 JS 已约 8.95 MiB，尚未计粗体/斜体/emoji |
| 隔离 npm 工具目录 | 44 个包，共 47,833,408 字节 | 开发评估目录，不等于浏览器产物或安装包增量；未加入产品依赖 |
| 测试 Chromium 的可执行目录 | 457,625,672 字节，约 436 MiB | 仅用于开发测试；若改为捆绑浏览器，要另算压缩包、更新、沙箱与三平台运行时，v0.3 不采用 |

系统打印不增加应用 JS/字体包体，但依赖系统 WebView/字体。本轮没有测量候选的新安装包增量，因为没有集成、构建或签名专用 PDF 产品。

## 5. 字体、引擎和运行时许可

候选 npm 精确版本、传递依赖版本/下载完整性保存在 `scripts/fixtures/pdf-evaluation/package-lock.json`，与产品 `pnpm-lock.yaml` 分离。评估库及下载字体全部位于忽略的 `test-results/pdf-engines/tools/`。原始候选/字体许可文本存于 [评估许可目录](verification/pdf-engine-licenses/)，**不是产品 SBOM 的新增依赖**。

- Paged.js 和 pdfmake 为 MIT；分发时要保留版权和完整许可，并复核实际浏览器 bundle 的传递组件。本次隔离清单还有 Apache-2.0、ISC、CC0、MIT/Zlib、Blue Oak、BSD-3-Clause 和 0BSD，不能仅拷两份 MIT 就宣称完整分发许可已满足。`png-js@1.1.0` 元数据缺 license，但包内实际文本为 MIT；JSON 单独记录这一证据。四个包没有在顶层常见文件名找到完整文本，需要进一步检查捆绑文本/来源。
- Noto 字体版本为 `2.004`，采用 SIL OFL 1.1。字体和许可下载使用固定上游 commit，SHA-256 校验；`OS/2.fsType` 无禁止嵌入、禁止子集或仅位图限制。输出中实际发现嵌入的 `NotoSansSC-Regular` 子集。允许随软件分发不表示可以单独出售字体；保留字体版权/OFL，字体修改、命名与 Reserved Font Name 条款需发行时复核。OFL 不使使用字体生成的文档自动受 OFL 约束。
- Regular 字体 cmap 实测没有本例三个 emoji。要支持 emoji，必须选择可分发的回退字体/图形方案并测试颜色、组合序列、授权和体积；不能复制 Windows Segoe UI Emoji 当作跨平台字体包。
- 系统 CSS/Paged.js 输出里可见 Microsoft YaHei、Segoe UI、Consolas、NSimSun 等系统字体子集；emoji 还使用 Type3 字形资源。PDF 的嵌入与可视结果是事实，**不构成微软字体重分发授权**。产品不打包 Windows 字体；不同系统的字体输出及许可仍需各自复核。
- Paged.js 仍依赖系统打印或另一个 PDF 后端；使用开发 Chromium API 生成测试 PDF 不意味着 EasyM 已获得该 API。若以后捆绑 Chromium，必须新增 Chromium/第三方许可、更新和沙箱责任，不能以 Paged.js 的 MIT 覆盖它。

## 6. 三平台与后续集成门槛

| 路线 | Windows 本机证据 | macOS / Linux |
| --- | --- | --- |
| 系统打印 | Chromium CSS 实测；现有 Tauri `window.print()` 代码 | 依赖 WKWebView/WebKitGTK；原生保存/取消及分页仍待实机 |
| Paged.js | Chromium DOM 分页、受 CSP 约束、图片解码后复现缺失 | JS/DOM 路线可研究，打印桥和兼容性没有实测；不能宣称三平台验收通过 |
| pdfmake | Node >=20 探针和真实浏览器 Worker 均通过；后者不需产品携带 Node | 浏览器 JS 路线有迁移可能；字体字节可固定，WebKit Worker、保存和版面未实测 |

后续专用 PDF 开发应先冻结：按需 Worker 和任务身份、同一内存正文快照、AST 映射及静态降级预检、A4/Letter 页边距、字体粗斜体/emoji 回退、行内图片和尺寸限制、标题同页与表格长行策略、空白页检测、配额/超时/取消、独立原子保存与冲突检查。未知内容、缺图和缺字都应可定位，不能静默丢失。正式采用前补完整依赖/字体许可与 SBOM、三平台渲染/保存、隔离峰值内存和源文未变验收。

这些属于下一轮专用 PDF 的进入条件，本轮第七步不自动扩张为 PDF 集成。当前 DOCX、历史、批图以及 Markdown 数据格式不因本评估改变。

## 7. 复现与证据

安装开发依赖后，在仓库根目录运行：

```powershell
node scripts/setup-pdf-evaluation.mjs
node scripts/verify-pdf-engines.mjs
# 使用装有 pypdf/Pillow 的 Python 和本机 Poppler，路径按实际环境填写
python scripts/inspect-pdf-engines.py --poppler "C:/path/to/pdftoppm.exe"
```

setup 使用隔离 npm lock 执行 `npm ci --ignore-scripts`；首次需要网络下载测试库/固定字体，实际生成不请求远程资源。重建 PDF 的时间戳和文件散列可能变化；应对照页数、源样例 hash、字体 hash、完整性与可视结果。不要用原生对话框的页数去替换这份 Chromium 证据。

生成/渲染详情保存在忽略的 `test-results/pdf-engines/`；审查后可运行 `node scripts/record-pdf-evaluation.mjs` 冻结当前证据，不能只生成而跳过版面检查。仓库记录见 [第六步证据](verification/v0.3-step6-verification.json)，包含 18 个 PDF 的 SHA-256、页面尺寸、页数、完整性、字体、候选 bundle hash、44 个隔离包和许可来源。

评估流程、隔离 setup、18 份生成、109 页渲染、Worker CSP、取消、缺字体错误及重试均已完成；两个候选的当前适配都没有通过正式产品版面门槛。TypeScript 检查和新增 JS 语法检查通过。根产品锁文件、运行时依赖和原生程序均未改变；本步没有重复宣称前五步的全量测试或三平台 CI 已由这次评估重跑通过。
