# EasyM v2.0 第 4 步：验收与交付

分支：`feature/v2.0-step-4-conflicts`，从 main `4ac459d` 创建（第 3 步及其后的列表、Mermaid 修复已合并）。分三次提交：4A 行级自动合并、4B 冲突界面、4C 回滚与异常恢复。

维护者的两个决定：

- 两台设备改到同一处、无法自动合并时，原位保留一份，另一版本另存为冲突副本；不在正文里写 `<<<<<<<` 冲突标记。
- 两边改的是不同行、可以自动合并时，直接合并，事后在同步对话框里提示，不逐次确认。

## 4A：行级自动合并（`dac7522`）

以前两台设备改了同一文档，合并提交就整篇保留一份、另一份存为冲突副本，即使两边改的是不同段落。

- [`sync-merge.ts`](../src/core/sync-merge.ts)：同步专用的三方行级合并。
  - 合并提交由每台设备各自计算，必须字节一致，否则设备之间无法收敛。所以它复用 `planMerge`，但不设按时钟计的超时，只按输入大小（每份 2 MiB）和差异算法的内存上限限制。快慢机器对同一输入得到同一结果。
  - 以下情况不合并，退回原来的冲突副本：编辑区域重叠；正文不是 UTF-8；带 BOM 或 NUL；两边换行方式不一致或含单独的 CR。
  - CRLF 文档合并后仍是 CRLF。
- 图片按路径合并：只有一边改的取改过的一边，两边改成不同内容算冲突。结果只保留合并后正文实际引用的图片。每文档的图片元数据按显示路径同样合并。
- [`sync-log.ts`](../src/core/sync-log.ts) 的 `mergeSyncCommits`：两边都改了内容且共同版本已知时，先读出三份正文尝试行级合并；合并出的正文和元数据随合并提交一起上传。冲突原因新增 `merged`，同步对话框据此提示“已自动合并双方改动”。
- 同步写入不经过版本历史（`sync_local_write` 直接调用 `transaction::save`），所以界面不承诺“可在历史中查看合并前的版本”。

修复：几台设备会同时上传同一份合并结果，Nextcloud 对同一路径的并发 PUT 偶尔返回 404（实测 80 次中 7 次）。原生客户端和测试 Provider 都把 404 当作锁冲突处理：先读回对象并按摘要校验，存在即视为已上传，否则退避重试。原生往返测试增加了每个对象 8 路并发创建。

## 4B：冲突界面（`7d1c85c`）

以前冲突副本只在当轮报告里提一句，之后就没有入口了。

- 待解决冲突的记录（[`sync-engine.ts`](../src/core/sync-engine.ts)）：
  - 引擎状态新增 `conflicts`，随同步状态持久保存。旧版本的状态没有这个字段，读取时视为空列表；格式不对的条目直接丢弃。
  - 本机写在未保存编辑旁边的“同步副本”，记录为 `local`，同时记下磁盘当时反映的版本作为共同版本。
  - 合并提交产生的冲突副本记录为 `merge`。每台设备都能识别：先按“（冲突 xxxxxxxx）”文件名找候选，再用派生 ID 证明它确实是哪份文档的副本。改过名或改过内容的副本不会被错认。
  - 共同版本在打开冲突时才查：沿历史找到生成该副本的合并提交，取它的合并基准里这份文档的正文。
  - 原文档或副本任一方不存在时，条目自动移除。
- 同步对话框新增“待解决的冲突”。点“解决”读出双方正文和共同版本，有三个选项：
  - 保留本文档：只把冲突副本移到回收站。
  - 改用冲突副本：用副本内容替换本文档。
  - 逐处合并：复用现有的 [`MergePreview`](../src/editor/MergePreview.tsx)，标签改为“本文档 / 冲突副本”；外部修改对话框的文字不变。
  - 找不到共同版本时，只提供前两个整篇选项。
- 写回（原生 `sync_local_resolve`，在文档写队列内执行）：
  - 先核对本文档和副本的版本，任一方在用户选择之后变过就不做任何改动。
  - 本文档正文要变时，先把原来的正文存进应用内回收站，命名为“<文件名> (解决前 <年月日-时分秒>).md”，再保存结果。
  - 最后把冲突副本移进回收站。两个旧版本都能从回收站恢复；恢复“解决前”版本会得到一份独立的新文档。
  - 只要求关闭冲突副本的标签页（与删除规则一致）。本文档开着也能解决：有未保存编辑时拒绝，没有时写回后原位重新加载。
  - 下一轮同步发布结果和副本的删除，冲突从列表中消失。

## 4C：回滚与异常恢复

以前远端回滚、设备身份被复制或记录不连续时，同步暂停，但“继续同步”只会再次遇到同样的错误。

- 暂停原因有了说明（[`sync-native.ts`](../src/platform/sync-native.ts)），并且都注明“本机文件没有改动”：
  - `rollback`：服务器上的记录比本机记住的旧，例如服务器从备份恢复。
  - `device_conflict`：另一处安装在使用本机的设备身份，例如复制了整个配置。
  - `not_descendant`：服务器记录与本机不连续。
  - `state_mismatch`（新）：本机同步状态属于另一个设备身份，通常是上次重新加入被中断。它从原来的 `identity_mismatch` 中拆出；工作区身份与绑定不符仍是 `identity_mismatch`，重新加入解决不了，不提供按钮。
  - `missing_object`：服务器缺少同步数据。应用会停在当前状态，不写半份文件，下一轮重试。
- “以新设备身份重新加入”（上面前四种原因时显示）：
  - 原生 `sync_rejoin` 只给绑定换一个新的设备 ID；凭据、服务器地址和对象缓存不变。旧设备头留在服务器上，它的提交仍是其他设备的祖先。
  - [`rejoinState`](../src/core/sync-engine.ts) 为新 ID 重建引擎状态，保留延后删除和待解决的冲突：
    - 磁盘上次完整反映的提交仍在服务器历史里时，保留为基准（`device.base`）。本机之后的修改按普通修改发布，能自动合并的就合并，不产生多余副本。
    - 基准已不在服务器历史里（例如回滚丢掉了它）时，不设基准。所有文档按两边都改过处理，与服务器不同的内容另存为冲突副本，不会互相覆盖。
  - [`runSyncPass`](../src/core/sync-log.ts) 只在基准确实能从远端设备头到达时接受这种首次提交；发布成功后清除 `base`。
  - 重新加入中途失败时，控制器按原生端当前的绑定重启；如果状态没来得及改写，下一轮报 `state_mismatch`，可以再次重新加入。

## 未验证与已知限制

- 没有在原生 GUI 上实机操作：系统凭据存储、TLS 证书错误、macOS/Linux 上 `tauri://` 下的同步界面都还没验证。端到端检查用的是行为与原生命令一致的目录宿主，界面检查用的是确定性 IPC。
- 完整回归 `verify:regression` 本机没有跑完（超过工具 10 分钟限制），交给 CI。
- 同步写入不生成版本历史快照；解决冲突时的旧版本靠应用内回收站保留。
- 行级合并只处理正文不超过 2 MiB、单一换行方式的 UTF-8 文档；其余情况仍保存为冲突副本。
- 冲突界面一次处理一个冲突；“改用冲突副本”整篇替换，不迁移副本独有的图片元数据（副本与原文档在同一目录，图片文件本身已在磁盘上）。
- 重新加入后旧设备头仍留在服务器上，设备数量计入 64 台上限；清理旧设备头留到第 5 步的设备管理。
- 大工作区的耗时和请求数仍留到第 5 步测量。
