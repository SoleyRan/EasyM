## 1. 目标与边界

### 1.1 用户目标

用户能够在没有账号和网络的情况下：

1. 打开一个已有的 Markdown 文件或创建未命名文档。
2. 用 Markdown 源码编辑，并看到即时渲染结果或源码与预览分屏。
3. 使用工具栏插入常用 Markdown 结构，而不必手写全部标记。
4. 粘贴、拖入或选择 PNG/JPEG 图片。
5. 双击文档中的图片，只编辑当前插入实例的应用副本。
6. 应用、取消或撤销图片修改，并确认原始图片不会被覆盖。
7. 保存、关闭、重新打开后恢复正文、图片引用和草稿状态。

### 1.2 明确不做的内容

以下能力不属于 v0.1，界面中不得以已完成功能的形式出现：

- Web、Android、iOS、账号、云同步、分享和实时协作；
- 插件市场、任意脚本、MDX、AI 和远程模型；
- DOCX、专用 PDF 引擎、批量图片处理和完整版本时间线；
- 表格结构化编辑、全文搜索、模板中心、三方合并；
- 修改磁盘原图、覆盖相册照片或自动删除历史资源；
- 对 CommonMark/GFM 之外语法的完整编辑保证。

系统打印、全文搜索和更多办公功能可以在后续版本接入。v0.1 可以保留可扩展接口，但不能为了这些预留功能增加不可验证的实现复杂度。

### 1.3 平台策略

产品目标平台仍为 Windows、macOS、Linux。v0.1 采用“一个平台完整纵向切片，其他平台验证关键路径”的策略：开发和自动化基线先在 Windows 建立；在宣布 v0.1 可发布前，至少在 macOS 和 Linux 各完成打开、中文输入、图片应用、保存恢复四条手工回归路径。平台差异必须通过能力检测和用户提示处理，不能假设三个 WebView 行为完全一致。

## 2. 冻结的产品决策

### 2.1 正文与视图

- Markdown 原始文本是唯一正文来源。
- AST、HTML、图片预览和大纲都是派生数据，不能反向覆盖整篇正文。
- v0.1 提供即时渲染、源码、分屏三种视图。
- 默认视图为即时渲染；若技术验证不能满足光标、中文输入或源范围要求，必须降级为源码视图默认、分屏可用，并在版本说明中记录限制。
- 切换视图不重写文件。打开后不编辑再保存时，原始字节、编码、BOM 和换行策略必须保持。

### 2.2 文件与资源

- 首期支持普通 `.md`/`.markdown` 文件和工作区目录。
- 首期图片输入保证 PNG、JPEG；文件类型以解码结果和 MIME 为准，不只相信扩展名。
- 磁盘源图和剪贴板图像均先复制到应用管理的源副本，任何图片编辑都从源副本生成新的显示副本。
- 每个图片插入具有独立 `instanceId`。同一资源插入两次，修改一次不得改变另一次的引用。
- Markdown 默认使用相对路径图片引用；不把图片尺寸或编辑历史只存于数据库。
- 元数据目录固定为工作区下的 `.easym/`，但正文即使缺少该目录也必须可读。

### 2.3 可靠性

- 正文保存使用同目录临时文件、刷新/关闭句柄和平台对应的安全替换策略。
- 图片文件写入成功后才提交正文引用变更；任一步骤失败都保留旧正文和旧引用。
- 已命名本地文件使用 1.2 秒闲置合并自动写回；未命名/恢复文档自动保留草稿，首次通过 EM 菜单另存为。保留 Ctrl/Cmd+S 强制保存与关闭前保存；冲突、写入失败或混合换行转换需用户处理。
- 外部修改不能静默覆盖未保存的本地编辑；v0.1 至少提供“重新加载外部版本”“保留本地并另存冲突副本”两个动作。
- 取消图片操作不得创建文档可见的新资源引用。

## 3. 用户界面与交互规格

### 3.1 工作区布局

桌面窗口由以下区域组成，允许收起左、右侧栏：

- 顶部单行 EM 图标与文档标签：EM 菜单提供文件操作，标签显示文件名及未保存标记。移除独立保存/当前路径行。
- 左侧工作区栏：打开工作区、文件树、打开文件入口。
- 中央编辑区：标签页、视图切换、编辑工具栏、正文。
- 右侧辅助栏：文档大纲；选中图片并进入编辑时显示图片操作面板。
- 底部状态区：当前视图、编码/换行提示、保存状态和错误提示。

v0.1 不显示云分享、协作成员、插件和 AI 入口。窗口尺寸变化时，中央编辑区优先保留；图片面板无法容纳时改为模态面板，而不是压缩编辑区到不可用宽度。

### 3.2 三种视图

| 视图 | 必须行为 | 允许的降级 |
| --- | --- | --- |
| 即时渲染 | 段落离开后显示排版结果；光标进入时显示可编辑源语法；图片可单击/双击 | 暂时退化为源码段落并保留预览；不得丢文本 |
| 源码 | 显示完整 Markdown、注释、Front Matter、未知语法和原有换行 | 不提供所见即所得的隐藏语法 |
| 分屏 | 左侧源码、右侧预览；两侧通过源位置同步；图片操作定位原节点 | 预览不可用时保留左侧源码并显示错误 |

即时渲染的最小实现可以按块渲染，而不要求建立完整富文本编辑器。块的身份由源范围和文档文本修订号共同确定；文本发生变化后不能使用过期范围提交命令。

### 3.3 编辑工具栏

v0.1 工具栏只包含以下命令：加粗、斜体、标题级别、无序列表、有序列表、任务列表、引用、代码块、插入链接、插入图片、撤销、重做。命令必须通过文档核心产生源范围补丁，不得读取 HTML 再反向生成全文 Markdown。

没有选区时，命令应插入可继续输入的最小占位文本；有选区时只包装选区。命令失败（例如源范围在外部修改后失效）必须返回可识别错误并保持原文本。

### 3.4 中文输入与键盘

- 输入法组合期间只接收文本编辑事件，不触发自动补全、自动闭合或块级转换。
- Windows/Linux 使用 Ctrl 快捷键，macOS 使用 Cmd；显示快捷键随平台变化。
- 自动转换只允许发生在组合提交完成后，并可在设置中关闭。
- 所有工具栏命令必须有键盘等价路径；图片裁剪、尺寸和倍率必须可用键盘输入。
- 图片操作面板的焦点顺序、标签和错误文本可被屏幕阅读器读取。

## 4. Markdown 语法与文档模型

### 4.1 v0.1 语法基线

解析基线为 CommonMark，开启 GFM 表格、任务列表和删除线的渲染支持。首期保证编辑和往返保留的结构包括：标题、段落、强调、链接、图片、引用、列表、任务列表、代码块、分隔线、表格、删除线、HTML 注释、Front Matter 和未知片段。

数学公式、脚注、Mermaid、执行型 HTML/MDX 不属于 v0.1 的可编辑保证。未知语法以原始文本显示；解析失败不得清空或规范化该片段。

### 4.2 文档状态

应用层文档状态至少包含：

```ts
type DocumentId = string
type ResourceUri = string

interface DocumentState {
  id: DocumentId
  uri: ResourceUri | null
  text: string
  textRevision: number
  baseRevision: string | null
  encoding: "utf-8" | "utf-8-bom" | "unknown"
  lineEnding: "lf" | "crlf" | "mixed"
  dirty: boolean
  draftAvailable: boolean
}
```

`textRevision` 只用于当前内存文本和源范围映射；`baseRevision` 是文件提供者返回的不透明版本标识，不能用大小比较判断新旧。`dirty` 由文本或待提交资源变化决定，不由文件修改时间单独决定。

### 4.3 源范围补丁

核心编辑命令输入当前 `textRevision`、选区和命令参数，输出一个或多个不重叠补丁：

```ts
interface TextPatch {
  from: number
  to: number
  insert: string
}

interface EditCommandResult {
  baseTextRevision: number
  patches: TextPatch[]
  selection?: { anchor: number; head: number }
}
```

宿主只在 `baseTextRevision` 仍为当前值时提交补丁。补丁应用后递增 `textRevision`，重新解析派生数据。文档保存不执行全篇格式化；若工具命令无法安全定位目标，只返回错误而不猜测。

## 5. 图片导入与副本编辑

### 5.1 支持的输入路径

v0.1 支持：剪贴板截图、剪贴板图片文件、从文件树拖入、系统文件选择器插入。网络图片只保留原链接，不能直接对远程内容进行像素编辑；用户需要编辑时必须先导入本地副本。

图像导入时读取 MIME、尺寸、方向和像素上限。JPEG 的 EXIF 方向在进入编辑器前归一化；透明图优先以 PNG 保留。解码失败、格式不支持、尺寸超限和内存不足都返回明确错误，不插入无效引用。

### 5.2 资源命名与目录

未命名文档的资源先写入应用草稿目录。文档第一次保存到工作区时，资源和 `.easym/images.json` 一起迁移，并把正文引用更新为目标工作区中的相对路径。已命名文档直接使用：

```text
workspace/
├── note.md
├── assets/
│   ├── img-<instanceId>-original.png
│   ├── img-<instanceId>-v1.png
│   └── .originals/
│       └── img-<instanceId>-source.png
└── .easym/
    └── images.json
```

文件名由应用生成并做路径安全校验；不得使用用户输入拼接 `..`、绝对路径或设备路径。资源写入前检查目标位于已授权工作区内。

### 5.3 图片编辑面板

双击预览图片或分屏右侧的图片，打开对应实例的图片面板。面板提供：

- 裁剪：自由比例、1:1、4:3、16:9，拖动裁剪框和数值输入；
- 尺寸：宽、高像素输入，锁定宽高比；
- 旋转：顺时针 90°；水平翻转、垂直翻转；
- Alt 文本编辑；
- 查看倍率（只影响面板预览）；
- 恢复源副本、取消、应用修改。

预览操作只保存内存中的 `ImageRecipe`。应用前显示“图片修改待应用”，应用后才生成显示副本和正文补丁。标准 Markdown 模式不写显示宽度；输出尺寸是图片像素尺寸，不等于文档排版宽度。

### 5.4 图片契约

```ts
interface ImageRecipe {
  version: 1
  orientationNormalized: boolean
  crop?: { unit: "sourcePixel"; x: number; y: number; width: number; height: number }
  rotateDegrees: 0 | 90 | 180 | 270
  flipHorizontal: boolean
  flipVertical: boolean
  resize?: { width: number; height: number }
  output: { mime: "image/png" | "image/jpeg" }
}

interface ImageInstance {
  instanceId: string
  documentId: DocumentId | null
  sourcePath: string
  sourceHash: string
  displayPath: string
  recipe: ImageRecipe
  referenceRevision: number
}
```

裁剪坐标以方向归一化后的源像素为基准。处理顺序固定为：方向归一化 → 裁剪 → 旋转/翻转 → 重采样 → 编码。v0.1 不要求不同平台生成逐字节相同的图片，但必须产生几何上正确、可解码且与契约一致的结果。

### 5.5 图片应用事务

图片应用按以下顺序执行：

1. 校验实例仍对应当前文本和资源。
2. 从不可变源副本读取并按 recipe 生成临时显示文件。
3. 刷新并验证临时文件可读、MIME、尺寸和哈希。
4. 将临时文件安全移动为新的显示副本。
5. 更新 `images.json` 临时文件并验证 JSON。
6. 在当前文本中只替换目标图片节点的路径和 Alt 文本。
7. 保存正文；正文成功后提交元数据临时文件。
8. 删除无引用的临时文件，保留旧显示副本供撤销或恢复。

正文保存失败时，旧正文和旧引用保持不变；新资源可留在待清理列表中，但不能被当作当前版本。元数据保存失败时保留正文可读性，并在下次打开时提示需要修复元数据。应用事务必须记录 `operationId`，重试同一操作不得生成重复的正文引用。

取消、关闭面板或处理失败都丢弃预览状态，不修改 Markdown。撤销通过恢复旧图片引用和旧 `ImageRecipe` 完成，不覆盖源副本。

### 5.6 v0.1 图片元数据

`.easym/images.json` 使用 `schemaVersion: 1`。它只记录恢复图片所需的信息，不是正文的替代存储：

```json
{
  "schemaVersion": 1,
  "instances": [
    {
      "instanceId": "img-01J-example",
      "documentId": "doc-example",
      "sourcePath": "assets/.originals/img-01J-example-source.png",
      "sourceHash": "sha256:...",
      "displayPath": "assets/img-01J-example-v1.png",
      "recipe": {
        "version": 1,
        "orientationNormalized": true,
        "crop": { "unit": "sourcePixel", "x": 0, "y": 0, "width": 1200, "height": 800 },
        "rotateDegrees": 0,
        "flipHorizontal": false,
        "flipVertical": false,
        "resize": { "width": 1200, "height": 800 },
        "output": { "mime": "image/png" }
      },
      "referenceRevision": 1
    }
  ]
}
```

路径必须是工作区相对路径；`sourceHash` 针对源副本字节；`referenceRevision` 用于检测正文中的实例引用是否仍是应用操作的目标。读取到未知的更高 `schemaVersion` 时，v0.1 只读打开正文和当前图片，不覆盖元数据，并提示使用更新版本恢复历史。

### 5.7 图片与文档状态

界面必须区分以下状态，避免用户把预览误认为已保存：

| 状态 | 含义 | 可执行动作 |
| --- | --- | --- |
| 图片未选中 | 当前没有图片操作 | 继续编辑 |
| 图片预览中 | recipe 只存在内存，正文未变化 | 应用、取消、恢复源状态 |
| 图片生成中 | 后台正在处理临时资源 | 取消任务；禁止重复应用 |
| 图片已生成待保存 | 新资源已验证，正文补丁尚未提交或正在提交 | 等待保存结果 |
| 图片已应用待保存 | 正文已指向新副本，但文件尚未落盘 | 保存、撤销 |
| 图片应用完成 | 正文、显示副本和元数据均已提交 | 继续编辑 |
| 图片应用需恢复 | 某一步失败，存在旧版本和待清理临时资源 | 重试、恢复旧引用、查看诊断 |

图片面板和底部状态区使用用户可理解的文字，例如“图片修改待应用”“图片已应用，正在保存”“保存失败，原版本仍保留”。

## 6. 工作区、保存与恢复

### 6.1 工作区识别

工作区由用户显式选择的目录确定。核心代码只使用 `ResourceUri` 和工作区相对路径；平台适配器负责把它们映射到 Windows、macOS 或 Linux 文件 API。应用不得把绝对路径写入工作区 JSON，日志也应脱敏用户名和令牌。

### 6.2 打开与保存

打开文件时记录原始字节哈希、编码、BOM、换行和文件提供者版本。保存流程为：

1. 读取当前文件并复核版本/哈希；发现外部变化则进入冲突流程。
2. 按原文件编码和换行策略编码当前文本。
3. 写入同目录唯一临时文件并刷新。
4. 重新校验临时文件内容哈希。
5. 使用平台安全替换策略提交。
6. 更新 `baseRevision`，清除 `dirty`，记录最近草稿快照。

已有文件不因编辑器偏好自动改成 LF 或 CRLF。混合换行文件在 v0.1 默认原样加载；发生编辑后提示用户选择保留原策略或统一为 LF，默认不得静默统一。

### 6.3 自动保存与草稿

已授权本地文件在停止输入 1.2 秒后自动写回，使用最后成功保存的版本检查外部冲突。写入串行且不阻止正文输入，期间的新编辑留待下一轮；中文组合输入、图片操作与关闭决策期间暂停。写入冲突/失败或混合换行转换暂停自动写回，保留草稿及提示，需手动保存/另存/加载外部版本处理。新建或恢复文档不自动弹出选择器，由 EM 菜单首次另存为；浏览器仅自动保留草稿，显式下载副本。文本变化后另采用 700 ms 合并自动保存草稿。草稿放在系统应用数据目录，和用户工作区分离；草稿包含文档文本、文件身份、资源引用、未完成图片操作和最后一次已知版本。正常退出和失焦时再次尝试刷盘，但不能依赖窗口关闭事件。

重启发现草稿版本比磁盘版本新时显示恢复对话框：恢复草稿、打开磁盘版本或另存为新文件。恢复前保留磁盘文件，不直接覆盖。用户选择放弃草稿后才清理对应草稿记录。

### 6.4 外部修改

文件监听是平台能力；不可用时在保存前主动检查。无本地改动时可以重新加载外部版本；有本地改动时至少提供保留本地并另存冲突副本。v0.1 不实现三方合并，但必须保存本地草稿和外部版本，不能静默覆盖任一方。

### 6.5 撤销、重做与操作边界

撤销栈属于当前会话的文本和图片引用操作，不等同于持久版本历史。普通输入按编辑器合并策略形成撤销组；工具栏命令、图片应用、Alt 文本更新和恢复源状态各形成一个可撤销操作。撤销图片应用只恢复旧引用和旧元数据，不删除仍可能被历史或草稿引用的资源。重做必须在当前文档修订号连续时执行；发生外部加载、冲突解决或重新打开后，清空当前会话撤销栈并保留草稿。

保存成功不会清空撤销栈。关闭窗口前若存在未保存文本、待提交图片或可恢复草稿，必须提示用户保存、继续退出或取消退出。

## 7. 分层实现方案

### 7.1 模块边界

```text
ui-shell (React)
  ├─ editor-adapter (CodeMirror 6、视图和源范围映射)
  ├─ application-services (文档、图片事务、草稿、保存状态)
  ├─ document-core (纯 TypeScript：解析、命令、补丁、序列化策略)
  └─ platform-adapter (Tauri/Rust：文件、剪贴板、图片、窗口)
```

`document-core` 不依赖 Tauri、Node、DOM 或系统文件。UI 不直接写磁盘；所有写入都通过应用服务和平台适配器。图片处理、文件 IO 和哈希计算放在后台任务，不能阻塞编辑输入。

### 7.2 技术基线

| 层 | v0.1 选择 | 约束 |
| --- | --- | --- |
| 桌面壳 | Tauri 2 | 只开放最小文件、剪贴板和窗口权限 |
| 界面 | React + TypeScript | 共享组件不携带平台路径假设 |
| 编辑器 | CodeMirror 6 | 一个文本状态支撑源码、分屏和即时渲染 |
| Markdown | unified/remark/rehype 或等价受许可实现 | CommonMark + GFM；危险 HTML 清理 |
| 图片 | Rust image crate 或等价已审查实现 | 限制像素、内存和输出格式 |
| 元数据 | 版本化 JSON | `.easym/images.json`，可手工读取 |
| 测试 | TypeScript 单测、Rust 单测、平台手工回归 | 契约测试覆盖所有 Provider |

具体依赖版本在项目初始化时锁定，并在发布包中生成依赖和许可证清单。v0.1 不引入 SQLite、DOCX 库、云 SDK 或插件运行时。

### 7.3 能力接口

```ts
interface StorageProvider {
  readText(uri: ResourceUri): Promise<DocumentSnapshot>
  writeText(request: WriteRequest): Promise<WriteOutcome>
  readAsset(uri: ResourceUri): Promise<Uint8Array>
  writeAsset(bytes: Uint8Array, mime: string): Promise<ResourceUri>
  move(uri: ResourceUri, destination: ResourceUri): Promise<void>
}

interface PlatformAdapter {
  capabilities: ReadonlySet<"folderAccess" | "fileWatch" | "clipboardImage">
  readClipboardImages(): Promise<ClipboardImage[]>
  pickDocuments(): Promise<ResourceUri[]>
  watch?(uri: ResourceUri, onChange: (event: FileChange) => void): () => void
}

interface ImageProcessor {
  transform(input: Uint8Array, recipe: ImageRecipe): Promise<ImageResult>
}
```

接口错误统一映射为 `permission_denied`、`revision_conflict`、`resource_missing`、`unsupported_capability`、`quota_exceeded`、`invalid_data`、`cancelled` 和 `io_failed`。用户提示必须给出可执行的恢复动作；堆栈、路径和诊断细节只写受控日志。

## 8. 安全、隐私与资源限制

- 预览清理危险 HTML、事件属性、脚本、危险 URL 和未授权外部资源。
- 图片只从用户明确选择的文件、剪贴板或工作区读取；文档中的任意路径不能获得写权限。
- 工作区相对路径拒绝路径穿越、绝对路径、设备路径和符号链接越界；实际解析后再次检查是否位于授权根目录。
- 图片解码限制压缩文件大小、像素总数、单边尺寸、解码内存和处理时长，防止恶意图片耗尽资源。
- 默认不联网、不上传正文、图片、剪贴板或诊断信息；远程链接使用系统浏览器打开。
- 崩溃日志默认不包含正文、图片字节、完整绝对路径和剪贴板内容。
- v0.1 不加载任意插件和执行型 Markdown；Mermaid、脚本和 MDX 作为原文显示。

## 9. 测试与验收

### 9.1 必须通过的自动化测试

1. 打开后不编辑再保存，字节、注释、未知语法、Front Matter、引用式链接和换行保持。
2. 工具栏命令只产生目标源范围补丁，不改写无关内容。
3. 输入法组合事件期间不触发自动转换；中文、英文和 emoji 输入均可恢复。
4. 同一图片插入两次，编辑其中一个实例只更新一个引用。
5. 应用图片修改后源副本哈希不变；取消不创建正文可见新引用；撤销回到旧显示副本。
6. 图片生成成功但正文写入失败、正文成功但元数据写入失败、磁盘空间不足和进程中断都能恢复到可读状态。
7. PNG/JPEG 解码、EXIF 方向、裁剪边界、旋转翻转和锁定比例结果符合 recipe。
8. 草稿版本较新时能恢复；放弃恢复不会覆盖磁盘文件。
9. 外部修改与本地未保存修改同时存在时不会静默覆盖。
10. 删除 `.easym/images.json` 后正文和当前显示图片仍可读，并提示恢复历史受限。

### 9.2 平台手工回归

在 Windows、macOS、Linux 各完成以下场景：创建文档、打开已有文档、中文输入、源码/分屏切换、粘贴截图、双击裁剪、应用、取消、重启恢复。额外检查高 DPI、系统文件对话框、快捷键、文件权限、路径含空格和长路径。

### 9.3 性能门槛

v0.1 以常规办公文件为目标：5 MB 文本、100 KB 超长单行、100 张中等图片和 20 MB 单张图片进入测试样例。固定基准机上，普通输入的编辑响应 p95 目标不超过 50 ms；图片处理在后台运行且可取消。超过资源预算时应提示并保持旧版本，不以卡死或强制退出作为降级方式。

### 9.4 发布阻断问题

以下问题不能带入 v0.1 演示或发布构建：静默覆盖外部修改、源图片被改写、正文引用不存在的资源、取消操作改变文件、重启后无法恢复可用正文、危险 HTML 执行、路径越界、图片解码导致进程失控，以及中文输入组合被破坏。

## 10. 开发顺序与交付物

### 10.1 实现顺序

1. 建立 Tauri/React/TypeScript 工程、许可清单和最小 CI。
2. 先实现纯 TypeScript 文档核心：文本状态、解析、源范围补丁、撤销/重做和往返样例。
3. 接入 CodeMirror 6，完成源码模式、中文输入和分屏预览。
4. 加入即时渲染技术验证；若达不到门槛，保留源码/分屏作为 v0.1 稳定路径。
5. 实现本地文件保存、原子替换、草稿和外部修改检测。
6. 实现 PNG/JPEG 导入、源副本、图片面板、recipe 和事务提交。
7. 接入大纲、错误提示、键盘导航和最小无障碍标签。
8. 执行故障注入、三平台回归、依赖许可检查和打包验证。

### 10.2 v0.1 交付物

- 可运行的 Windows 开发构建和 macOS/Linux 回归构建；
- 本文对应的实现说明、已知限制和恢复路径；
- CommonMark/GFM、图片和故障注入样例集；
- 文档核心、StorageProvider、ImageProcessor 的契约测试报告；
- `.easym/images.json` 的 schemaVersion=1 示例和迁移说明；
- 锁定依赖、第三方许可证、SBOM 和构建校验信息；
- 已知问题清单，按数据损坏、功能缺失、平台差异和体验问题分类。

## 11. 冻结后的变更规则

v0.1 冻结后，新增功能不能直接挤入本阶段。以下变更必须记录设计变更说明并重新运行受影响的契约测试：

- Markdown 语法、源范围补丁或序列化策略变化；
- 图片 recipe、资源目录、实例身份或 `.easym` schema 变化；
- 保存、草稿恢复、外部冲突和事务提交语义变化；
- 平台权限、预览清理策略或图片资源限制变化。

只改变颜色、间距或不影响键盘/无障碍语义的界面调整可以独立进行。任何会改变正文、资源或恢复行为的 UI 操作都视为契约变更。

## 12. v0.1 完成判定

当且仅当以下条件同时满足，才能称为“v0.1 完成”：

1. 两个核心闭环可现场演示：Markdown 打开—编辑—保存—重启恢复；图片导入—双击编辑—应用/取消/撤销。
2. 正文唯一来源、图片实例隔离和源文件不可变三项不变量有自动化测试证据。
3. 保存失败、资源写入失败、元数据损坏、外部修改和进程中断有可执行恢复路径。
4. Windows 主路径稳定，macOS/Linux 关键路径通过回归，平台限制均有准确提示。
5. 没有发布阻断问题，已知限制、依赖许可和构建产物记录齐全。

达到上述条件后，才进入 v0.2 的文件树、大纲增强、搜索、模板、HTML/打印和办公管理功能评估。未达到条件时，优先修复可靠性和数据安全，不以增加按钮数量作为版本完成标准。
