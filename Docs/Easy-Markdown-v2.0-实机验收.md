## 准备

- 在临时目录复制 `Docs/samples/v2.0/`，不要在唯一原件上练习。
- 同步项需要两台设备（可以是不同平台），以及一台测试用 WebDAV 服务器：Apache 2.4.69 mod_dav_fs 或 Nextcloud 31.0.14，用测试账号。仓库的 `scripts/webdav/compose.yaml` 可在本机起两个测试服务，但只监听 127.0.0.1。跨机器测试需要一台局域网内其他设备可访问的服务器，例如把端口映射改为局域网地址的临时副本，或用自己的 Nextcloud。测试服务用的是 HTTP，只能在可信的局域网里使用。
- 升级项要用 1.0.0 安装包和一份复制出来的旧数据。

## 长时间离线试用

目的：在真实写作节奏下，确认长时间离线、多次重启后再同步，不丢内容、不出现多余副本。建议至少 7 天，两台设备，其中至少一台为非 Windows。

1. 第 1 天：两台设备连接同一个测试工作区，同步一次，记录两边文档数和候选 SHA-256。
2. 第 2–6 天：每天在两台设备上各断网写作，覆盖：
   - 新建和编辑文档；
   - 插入、裁剪图片；
   - 重命名、移动文档；
   - 移到回收站；
   - 至少一次两边改同一文档的同一段落。

   期间正常关机、重启，至少一次在保存后立即强制退出应用。
3. 第 7 天：先联网同步一台，再联网同步另一台，然后两边各再同步一次。
4. 核对并记录：
   - 两边的文档列表、正文和图片是否一致（可以用外部 diff 工具比对两边的工作区目录）；
   - 冲突副本的数量是否和预期的同段落修改次数一致；
   - 回收站内容是否符合预期；
   - 有无报错，诊断信息里的错误码。
5. 再做一轮：一台设备离线超过 3 天，另一台期间停用它；回来后确认它提示已被停用，重新加入后本机修改另存为副本，没有被覆盖。

只要出现内容丢失、静默覆盖、图片错位或文件损坏，就是发布阻断项。记录最短复现步骤，并附诊断信息。

## 如何执行和反馈

1. 从指定 CI 的 Artifacts 下载三个 `release-candidate` 包，先解压外层 artifact ZIP，再核对 manifest 里的提交、文件名、大小和 SHA-256。
2. 先备份日常文档、图片、历史。同步只用测试工作区和测试账号。
3. 真实输入法、原生对话框、系统凭据存储、打印、读屏都必须在目标机器上实际操作。未签名候选被系统阻止时，记录具体的提示文字。
4. 反馈时注明平台、候选 SHA-256、表格项目和结果。失败的项附上最短复现步骤、预期和实际表现、同步对话框里“复制诊断信息”的内容或截图。没操作过的项保留“待验”。修复后，用新提交的候选重验相关项。

## 发布判定

以下情况都会阻断发布：

- 保存或恢复时丢失内容；
- 同步静默覆盖或吞掉编辑；
- 图片、历史或同步数据损坏；
- 路径逃逸；
- 密码出现在文件、日志或诊断信息中；
- 必需的 CI 检查失败。

任何失败都先附上复现步骤、诊断信息和候选哈希，再修复，或者明确调整支持范围。不能把未验的项直接标成通过。

Beta 候选作为 GitHub 预发布公开前，至少需要：

- 同一候选三平台的 CI 全绿；
- Windows 和另外一个平台完成“同步与凭据”全部项目；
- 维护者确认签名和分发方式。

2.0.0 正式版需要：

- 三平台所有项目都有结果；
- 长时间离线试用完成；
- Beta 反馈中的阻断项已经关闭。
